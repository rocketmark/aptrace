## Sources and conflicts

Primary local sources: `docs/hardware/firmware-pin-function-map.md` and its generated JSON; `docs/replacement/mapped-pin-causal-gap-audit.md` and JSON; `docs/investigations/boot-and-hardware-bringup.md`, `motor-subsystem-unlock.md`, `motor-config-persistence.md`, `manual-mode-and-limits.md`; `docs/hardware/hardware-reference.md`; `research/generated/autopilot-replacement-gaps.json`; case `status.md`; `research/runs/agent/tmc5160-census-2026-09-26-r7.json`.

Two qualifications materially change implementation guidance:

1. **Enable ordering conflict resolved by direct instructions and fresh execution.** The pin-map/causal summary says FUN_000077a0 changes PB17/PB16 after delay. Actual instructions call digitalWrite at 0x77ac / 0x77b6 **before** `delay(50)` at 0x77bc; STEP/DIR output configuration follows at 0x77c8 / 0x77d2. `control-enable.json` confirms PB17/PB16 OUTSET at instructions 36/71, delay entry at 76, STEP/DIR DIRSET at 2136–2331. Use this direct sequence. Historical files remain unchanged.
2. **Startup universality is conditional on progress.** The historical “every boot, without exception” wording exceeds a static sole-exit argument. The startup loop's snapshot can be refreshed; termination is not established for every input history. The four HIGH writes occur on the startup routine's timeout exit, before STEP/DIR output configuration, as observed in this boot scenario. They are not a claim about power-on pin levels, indefinite startup waits, or bootloader execution. The pin-map's “exactly three functions” wording also excludes its own later documented startup writer; the known set includes FUN_00006968 plus the three runtime helpers.

## Implementation-oriented transition table

All four STEP/DIR pairs participate in runtime pin-mode changes, not just channel 0. “Enable” and “disable” below are legacy software roles. Values omitted by a helper are retained/unknown according to the prior state.

| ID / trigger | Ordered original-firmware behavior | Final logical state | Evidence scope |
|---|---|---|---|
| RF-CTRL-BOOT / FUN_00006968 timeout exit | Configure PB06, PB07, PB17, PB16 OUTPUT; write PB17 HIGH, PB16 HIGH, PB06 HIGH, PB07 HIGH; configure all STEP/DIR OUTPUT without explicit digitalWrite levels in that loop; configure timers | Four control outputs HIGH; initial STEP/DIR voltage not established | Existing static/discovery + fresh bounded boot |
| RF-CTRL-DISABLE-H / FUN_000077f8 | All eight STEP/DIR pins INPUT; PB06 HIGH, PB07 HIGH; delay(50); PB17 LOW, PB16 LOW; RAM 0x200000bc = 0 | PB06/07 HIGH, PB17/16 LOW, STEP/DIR INPUT | Fresh direct call + existing static |
| RF-CTRL-DISABLE-L / FUN_00007868 | All eight STEP/DIR pins INPUT; PB06 LOW, PB07 LOW; delay(50); PB17 LOW, PB16 LOW; RAM 0x200000bc = 0 | All four controls LOW, STEP/DIR INPUT | Fresh direct call + existing static |
| RF-CTRL-ENABLE / FUN_000077a0 | PB17 HIGH, PB16 HIGH; delay(50); all eight STEP/DIR pins OUTPUT; RAM 0x200000bc = 1 | PB17/16 HIGH; PB06/07 **untouched**, STEP/DIR OUTPUT | Fresh disassembly + direct call; correction above |

Each pair is written sequentially, not atomically. Neither disable helper contains a HIGH→LOW pulse on PB06/PB07; a transition between levels can occur across separate calls. Enabling does not restore PB06/PB07. The predecessor state therefore matters.

Known causes from the existing causal audit: aggregate connector-presence changes in sketch loop (calls 0x7918, 0x794c, 0x7962); ASCII J branches (calls 0x88e2 / 0x88d0) depending on three RAM flags; manual binary F0/E0 branches conditionally re-enable when previously disabled (calls 0x8274 / 0x82d6). These are static caller/control-flow findings. This session does not turn those conditions into a complete truth table for J or real motor-presence events. No new command-path reachability proof was manufactured.

## Startup, stop, reset and fault constraints

Observed application order: Reset_Handler 0xcc24 copies data, clears BSS, enables FPU; clock/peripheral setup 0xcdd8; main 0xcd90; setup 0x9464 → startup routine 0x6968 → radio init/probe → post-probe motor/platform initialization → setup's internal receive loop. MC4 clearing 0x20000060 permits setup to return to sketch loop 0x93fc. The “steady main loop” receive address 0x8960 can execute inside setup; observing it alone does not establish the MC4 handoff.

Fresh `application-boot.json`: timeout branch at instruction 64134; control OUTPUT requests at 64440, 64467, 64494, 64521; HIGH requests PB17/PB16/PB06/PB07 at 64555, 64583, 64618, 64652; STEP/DIR loop entry 64655. First receive call 378402, then 381341, 384252, 387163, 390074. These reproduce the documented milestones under the recipe assumptions. Run ends at 450000 instructions, `error_free=true`, `completed=false`, because a bounded continuing program exhausted its budget. No ISR is automatically delivered.

The ≥1800 millis threshold is relative to a refreshable snapshot, not a guaranteed 1.8 s power-on delay. Runtime helpers pass exactly decimal 50 to the millis-based delay. Fake ticks reproduce ordering, not elapsed hardware milliseconds. No DWT-derived pulse width is asserted.

Software timer stop is distinct from driver-control disable. FUN_00005858(channel) clears TC.CTRLA.ENABLE; a fresh channel-0 call seeded with 0x602 writes 0x600 and returns. Completion helper FUN_00005958 calls it and clears per-channel state; its decompiler's apparent 64-bit return/index is a known artifact documented in the motor dossier. Target-reached paths from FUN_00006338 and FUN_00005be8 call it. This is not a complete validated shutdown of all hardware.

The three control helpers do not themselves stop TC0–TC3 before changing GPIO direction/control values (bounded static bodies and complete direct calls). Therefore timer state may remain enabled while STEP/DIR pins are inputs, controls change, or outputs are restored. An ISR's actual occurrence during those intervals, latent pending events, output glitches and physical pulses are **unknown**. No race-free stop or STOP latency is established. Remote jog “stop is silence” describes its sender loop; current evidence does not establish a receiver dead-man timeout. Do not adopt silence as a replacement safety mechanism.

WDT library helpers exist: 0x9518 waits on synchronization and writes CLEAR=0xa5; 0x952c clears enable and acknowledges a flag; 0x95c8 configures/enables WDT, including a call from the held-input path inside 0x5dd0 followed by an infinite loop. The caller passes 200 and 0; this is a candidate reset/halt mechanism, not a measured 200 ms reset. No watchdog expiry, fault recovery, reset-cause handling or driver-fault response was executed. The code's presence is not evidence that all faults take a controlled stop path.

The updater AIRCR software reset and 1200-baud touch-reset are documented in hardware-reference.md. They do not establish the application's pre-reset motor behavior. Fresh disassembly at 0xd4dc shows a countdown at 0x20000224: on reaching zero it disables interrupts, stores boot magic 0xf01669ef to 0x2002fffc, preserves AIRCR priority bits and requests SYSRESETREQ. A raw-entry run seeded with countdown=1 reaches checkpoint 0xd508 after 20 instructions, with countdown=0, magic stored and AIRCR=0x05fa0004. This establishes the reset-request block under the seed, not who arms it in a USB session or whether motors stop before that point. The same `--call` attempt exhausted 20000 instructions because the CLI silently omits user `--stop-at` in call mode; that trace is preserved separately. PPB is outside the MMIO log window, so the request is evidenced by final memory plus disassembly, not an invented logged write. Reset execution, reset pin states, bootloader GPIO manipulation and handoff timing remain unmodeled/unverified. No bootloader behavior is inferred from the application image.

## Channel-0 timer-driven motion contract

TC0 base 0x40003800; IRQ107 handler 0x607c → 0x5be8 → pulse helper 0x5898 on its non-coordinated fast path. Other channels use TC1–TC3; the established MCU STEP/DIR architecture is retained.

`ch0-timer-init.json`, direct FUN_00005570(0), returns in 40 instructions. Writes: MCLK.APBAMASK OR 0x4000; TC0.CTRLA clear ENABLE; GCLK.GENCTRL7=0x306; PCHCTRL9=0x47; TC0.CTRLA=0x600; WAVE=1; NVIC IRQ107 priority=0 and enable bit; CTRLBSET=2; INTENSET writes 0 then 0x10; COUNT=0. In boot the mask write is 0xf000 because other enables already exist. Compare RMW results with their initial state, not a universal literal.

Local SVD interpretation: GENCTRL7 source DFLL, enabled, improved duty; channel 9 generator 7 enabled. CTRLA.MODE=COUNT16, prescaler field 6 = **DIV256**, ENABLE clear; WAVE=1 = MFRQ. INTENSET requests MC0 (0x10); the ISR also writes OVF (bit 0). A generic description saying both interrupt sources were enabled is stronger than this captured initialization. No autonomous timer source frequency is measured; record actual Hz as unknown. The documented `24,000,000 / value` computation in FUN_00006190 is a software scaling term, not independently established TC0 clock frequency.

Rate path: FUN_00005ee8 bounds its period-like RAM value at 0x2000007c to [20, 8000000], branches at 60001, and writes a scaled result at 0x200030e8; slow branch shifts right 7. FUN_000056e8's software mode arguments 1 / 0x40 produce CTRLA 0x102 / 0x602 after clearing ENABLE. By SVD these are DIV2 / DIV256 with ENABLE set; the argument 0x40 is **not a hardware divide-by-64 encoding**. This is a decompiler-assisted static interpretation of the retained function review, not a proven effective step-rate formula.

FUN_00005c00(0, period) writes the low 16 bits to CC0, requests READSYNC (CTRLBSET=0x80), waits, then compares COUNT under software scaling conditions; it can call the channel-0 service function before resetting COUNT. Fresh case period=10000 observes CC0=0x2710 and READSYNC, then remains in the wait through 20000 instructions. It is a **partial trace**, not a completed period update. No synthetic sync-completion hook was added to force success.

Pulse helper: adds signed step_delta[0] at 0x20000094 to live position 0x20002064. If the result is divisible by byte 0x20003099, writes STEP HIGH then LOW through 0xd388. Fresh direct handler-body case seeds delta=+1, divisor=1, STEP indices=29 2b 07 2d and otherwise zero RAM/MMIO: position 0→1; INTFLAG writes 0x10 then 0x11; PB10 OUTSET/OUTCLR mask 0x400, instructions 60/93, complete return at 108. Readbacks/alias writes follow memory semantics; 0x11 is the modeled RMW sequence, **not a statement of silicon W1C behavior**. This is direct function entry with an AAPCS return trampoline, not natural exception delivery or a full move. That distinction closes the old wrong-pin trace limitation only for this seeded channel-0 case.

Existing ramp evidence: FUN_00006fd8 commits only when abs(distance)>8, resets segment state and arms phase=1; ≤8 clears/no-ops. FUN_00008e18 / 0x6338 advance phase 1→2→3 and rate/target state. The busy/rate gate at 0x20001b14 remains unresolved; older static constant-reference searches and bounded watches found no nonzero writer; the [trigger request campaign](../investigations/trigger-misfire-failure-modes.md#targeted-request-campaign-an-overlooked-motion-initiation-path) now observes the original nonzero writer at0x5fa4 after profile-driven timer start. Computed-pointer writes and unobserved contexts are not excluded. Historical “no code path anywhere” wording is not carried into this contract. Exact acceleration/deceleration coefficients, full move counts, reverse move, direction GPIO value/setup before first step, pending-interrupt behavior, pulse width, jitter and completion latency remain unestablished. No full-movement test vector is exported.

## TMC5160 and electrical scope

The checkout changed during the investigation (initial fa32c4b, final 3750c35). The newly available `docs/hardware/AutoPilot_Continuity_Bench_Sheet.md` is the original measurement record, attributed to Mark Stalzer's “Pin Testing” screenshots dated 2026-09-21; the reconciliation documents are dated 2026-10-17. Neither date is silently treated as the actual measurement time, which is not independently established. No new measurement was made here.

Physical evidence now establishes **two** distinct muxes. Raw §3 records 0 Ω routes: Mux1 A4→TMC1 STEP17, A7→TMC1 DIR18, A9→TMC3 DIR18, A12→TMC3 STEP17; Mux2 A4→TMC2 STEP17, A7→TMC2 DIR18, A9→TMC4 DIR18, A12→TMC4 STEP17. Raw §4 associates both B legs with RJ45 #2/#4 for Mux1 and #1/#3 for Mux2 through reported diode/resistor paths, roughly 468–488 Ω. These are resistance/network observations, not proof that both legs are one copper net or a powered source-select truth table. The §4 “TMC #”/“TMC pin” row labels are inconsistent; §3's explicit pin17/18 measurements ground the mapping. MCU STEP/DIR-to-driver and physical XLR logical-channel mapping remain unknown.

Raw §5 records **TMC1** SD_MODE21 and SPI_MODE22 at 0 Ω to VCC I/O. Raw §7 records TMC1 CFG4/5/6 pins23/24/25 at 0 Ω to GNDANA. Raw §8 records TMC1 DRV_ENN28 connected to GNDANA, without its own resistance column; DIAG rows remain blank. These are reported strap observations, not a powered voltage/current/safety result. Broader claims about all four drivers in the summary are not independently supported by these TMC1-only rows. A measured grounded DRV_ENN is incompatible with simply assuming that the four firmware GPIOs directly drive that input on TMC1, but it does not establish all other devices' circuitry or lack of every MCU connection.

**Material raw/summary conflict:** current hardware-reference/pin-map narrative says serial/config pins13–16 were not measured and describes standalone/no-SPI operation. Raw §6 is populated: CSN_CFG3 pin13 → MCU package pins11,37,12,38 respectively for TMC1–4; shared SCK14 → MCU64, SDI15 → MCU63, SDO16 → MCU62. The lower per-TMC1 connection blanks do not erase this upper table. Treat these as **reported physical routing**, with exact net resistance and powered bus behavior not established by that table. Do not translate package pins to GPIO names without supporting local package evidence. The SD_MODE/SPI_MODE HIGH observations alone are not exported as “no SPI”: no authoritative local mode truth table was located to validate that narrative interpretation, and the reported serial routes make the distinction implementation-relevant. Resolve the mode interpretation from local device documentation before choosing a driver-configuration strategy. This does not reopen the established MCU STEP/DIR versus internal-ramp conclusion.

SERCOM2 radio SPI remains traced; SERCOM5 boot initialization does not demonstrate TMC transactions. The prior TMC agent run stopped `planner_prefill_exhausted`, `reconciled=false`: it is not exhaustive absence evidence. CURRENT / MICROSTEPPING command fields have display consumers and no traced hardware configuration effect; **lack of discovered hardware effect** does not establish absence of a wired bus. Current-sense topology/effective current, actual microstepping state, powered mode, DIAG/fault handling and the full initialization sequence remain unresolved. No safe current is inferred. Connector guard/raw MT probes and A,C,B,D digit order describe detection logic, not complete physical motor identification.

## Proposed replacement requirements (engineering proposals, not legacy observations)

- Gate first motor energization on confirmed current configuration, routing, active polarities, and reset/startup containment from the bench checklist. Unknown electrical conditions are requirements to resolve, not GPIO defaults.
- Use the recovered PB10/PB11 logical channel-0 mapping; keep physical connector identity configurable until continuity verifies it. Protect all other channels, since legacy control lines/pin-mode changes are shared.
- Design an explicit stopped state that halts step production and handles pending events before a measured routing/control transition. Establish STEP idle level and DIR setup/hold from applicable local device evidence or approved engineering requirements. These are replacement design choices requiring validation, not a requirement to reproduce an unsafe legacy ordering.
- Define USB STOP, communication-loss handling, watchdog/fault and reset sequencing explicitly. USB command semantics need not reproduce the legacy RF dispatcher. Application USB control is independent of updater reset behavior.
- Use the exported vectors for logical/register-order comparison within their scopes. Do not require instruction counts, fake tick cadence or undefined hardware state to match apfw2.
