# TMC5160 configuration gaps

POC0.1 has useful serial-interface software evidence. It still lacks a verified electrical test configuration and actionable device configuration values. IDs below are shared with the contract and bench plan. Legacy observed values are references, not safe defaults.

| Priority / ID | Question and why it matters | Can firmware analysis resolve it? | Minimum missing evidence / physical work | Gate |
|---|---|---|---|---|
| HIGH / TMC-G0 | What are the package GPIOs and supported SERCOM5 pinmux for package11/37/12/38/64/63/62? | Firmware establishes its own PB01/02/03 and four select requests, not a package pinout | Local authoritative ATSAMD51J19A 64-pin package and mux tables, including DOPO/DIPO restrictions. This is a documentation task; do not repeat continuity merely to replace a missing table | Before fixing hardware pin constants or driving candidate lines |
| HIGH / TMC-G1 | What do SPI_MODE/SD_MODE HIGH and CFG straps mean on the actual TMC5160A device? Are serial config and external STEP/DIR compatible in that mode? | No; native reads have no physical TMC model | Correct local device mode/SPI/power-domain documentation, followed by powered rail-relative mode-pin observations under approved conditions. Reuse recorded TMC1 continuity. Other devices remain unknown | Before hardware SPI access |
| HIGH / TMC-G2 | Can logic-only communication be non-energizing, with other channels contained? Grounded DRV_ENN is not an established disable | No; application writes do not prove board power/current paths | Hardware engineer documents supply-domain sequencing, isolation/back-power analysis, actual output-disable arrangement and all-channel containment, grounded in device documentation and circuit evidence | Before powering an SPI test; blocked pending review |
| HIGH / TMC-G3 | Are shared lines and separate selects suitable and independent? | Existing code proves separate logical GPIO requests only | Reconcile endpoint metadata from existing §6; characterize any intervening parts/pulls, check powered idle/selected levels and nonselected output release against documented requirements; verify one CS without disturbing others | Before first live SPI transaction |
| HIGH / TMC-G4 | Can a documented register be read correctly? | Static/concrete evidence proves legacy read attempts, not response validity | A local device SPI/register reference selecting a named readable register, request/response pipeline, expected mask/content or oracle; one bounded captured transaction with reproducible expected response. Do not invent an address, value, voltage or clock | Establishes functional interface before relying on configuration/diagnostics |
| HIGH / TMC-G5 | What is the effective current limit and actual sense network? | Current field reaches serial setters, but an emulated coefficient is not a measured resistor/current | Identify sense resistors/analog topology and applicable device current equations; approved motor/power-stage ratings; documented first-test current budget and measurement | Blocks first motor energization |
| HIGH / TMC-G6 | What configuration is actually active: chopper, microsteps, hold/run current, enable and reset state? | Legacy raw write selectors/words and current/microstep consumers are available. Register semantics and electrical state are not | Device register reference plus validated readback, known reset/strap conditions and full sequence of configuration writes. Never assume defaults survived startup | Blocks energization; some readback can follow G0–G4 |
| HIGH / TMC-G7 | Are reset/startup/STOP/fault transitions non-energizing and isolated? | Application sequence is bounded evidence; bootloader, hardware reset and asynchronous state are not modeled | Approved waveform/current observations covering reset release, startup, selected/unselected drivers, communications failure and fault handling. Obtain bootloader evidence only if its behavior is an implementation requirement | Before first powered motor test |
| MEDIUM / TMC-G8 | Which logical channel corresponds to bench TMC1 and a physical XLR motor output? | Software order0,1,2,3→objects20a0,21d8,213c,2274 is established; physical join is not | G0 package mapping plus existing CS measurements should resolve part of the join without a repeated continuity matrix. Only missing STEP/DIR-to-driver and driver-to-XLR relationships need new probing | Before attaching/controlling one motor |
| MEDIUM / TMC-G9 | Which status/fault indications can replacement firmware trust? | Wrapper selects0x6f and extracts bits29/30; physical meaning/oracle missing | Device fault/status definitions and validated readback, then bounded fault-response verification in approved conditions; DIAG routes only if required | Basic SPI read validation first; comprehensive diagnostics later |

The original current/microstep “display-only” gap is **reconciled at the software-consumer level**:0x7514→0xae60/0xb070 and serial write methods execute during boot. It remains a gap at the electrical-value level. This distinction prevents unnecessary protocol rediscovery while retaining the current-safety gate.

Questions that can proceed with existing APTrace: interpreting a specific observed raw selector after the authoritative local register reference is supplied; checking a named caller/setting against the captured startup state; producing a bounded software comparison for that setting. No new APTrace feature was demonstrated necessary to answer those software questions.

Questions requiring new physical evidence are G1–G9's electrical parts. Questions requiring missing documentation are G0/G1/G4/G5/G6/G9. Existing timer/IRQ modeling and LID limitations remain disclosed in the readiness assessment; they are not a reason to implement a new SPI simulator or start broad census work here.
