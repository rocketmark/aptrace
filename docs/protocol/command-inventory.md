# Command Inventory (curated)

**Authoritative source data**: `research/autopilot_static_inventory/commands.csv`
(exhaustive) and `commands.md` (readable subset, high-confidence entries
only). This file is a curated summary pointing at that data — for the full
table with confidence ratings and notes, read the CSV/MD directly.

**Execution-confirmed** (see [`docs/protocol/protocol-overview.md`](protocol-overview.md)):
`&`, `G`, `!`, `S` — the AutoPilot dispatcher's real comparison instructions
require exactly these ASCII values to reach each command's handler.
**Also execution-confirmed, concretely, through the real live RX path**
(a separate, later line of investigation — see each command's own row
below for its specific evidence doc): `MC4`, `LL1`/`LL2`, `D`, and
(for its `mode=0x62` bulk-push form only, both sender and receiver, plus
the downstream real `G` mode-1 consequence) `'+'`. **Full transaction
(real Remote sender -> real AutoPilot dispatch/state/response -> real
Remote parser) confirmed via `tools/unicorn/virtual_link.py`**: `!0\|`/
`!1\|` (`bang`), `I<channel><mode>\|` (`i`), and `I9\|`/`I1\|` (`i9i1`).
Everything else below is static-analysis-only.

| `!0\|` / `!1\|` | Remote -> AutoPilot | Bulk state/config query. **Execution-confirmed end to end, both mode digits** (`tools/unicorn/virtual_link.py bang`): AutoPilot's `0x87b2` dispatch check never inspects the mode digit — identical outcome for `!0\|`/`!1\|` — and `0x8c70` always emits exactly 11 comma-terminated fields; Remote's `0xc440` parser calls its field parser exactly 10 times then unconditionally marks itself done, **never attempting field 11**. The 11th field + its comma are left byte-for-byte unconsumed in the real RX ring buffer (confirmed via real read/write-pointer inspection) — silent on both sides, no error/assert. | `TR0\|` / `TR1\|` | Remote -> AutoPilot | Boolean family (false/true). **`TR0\|`'s Remote-side sender confirmed** (`manual-mode-and-limits.md`): same shared settings/row-action widget, sent 3x on a different row selection. **AutoPilot-side effect now CONFIRMED** (found while tracing the trigger-input reported bug): the dispatcher's real `'T'`→`'R'`→`<digit>` branch (`0x84fa`-`0x8512`) writes the parsed digit into `0x20003120` — this is the enable byte gating whether the trigger-status `T<>,<>,\|` frame (below) is ever sent at all (`TR1\|` arms it, `TR0\|`, the default, disarms it) — see [`trigger-input.md`](../investigations/trigger-input.md) | inline state change |
| `W0\|` / `W1\|` | Remote -> AutoPilot | W-family subcommand | `W1` -> up to five `#` (event 17), conditional |
| `R0\|` / `R1\|` / `R2\|` | Remote -> AutoPilot | R-family state | `R0`->`@`, `R1`->`@@` (event 4) |
| `MC<0-3><a>,<b>,<c>,<d>,\|` | Remote -> AutoPilot | Motor configuration, one channel — does **not** unlock the motor subsystem (see next row). **Remote sender confirmed**: a single function, `FUN_00005a8c` (mando868), builds every `MC` frame in the image (the sole such builder, confirmed by four independent full-image scans) — the `<0-3>` call site is `0x10cbe` in `FUN_00010698`, the Remote's motor-settings numeric-row editor, sent every time the user clicks out of an edited row (`"CURRENT (mA)"`/`"STEPS/S MAX"`/`"MICRO-STEPPING"`/`"RETURN SPEED"`), not once per motor. Sent three times with no ack wait, unlike `'+'`. See [`motor-subsystem-unlock.md`](../investigations/motor-subsystem-unlock.md) | — |
| `MC4<a0>,<b0>,<c0>,<d0>,...\|` | Remote -> AutoPilot | Motor configuration, all four channels; **the only command in this firmware image that ends the boot-phase loop and hands control to the loop containing the motor-phase/ramp/monitor subsystem** (clears `0x20000060`) — execution-confirmed, concretely, including the real handoff to `FUN_000093fc`, and reconfirmed this pass using a real **Remote-produced** frame (not AutoPilot-side-fabricated). Of its 4 per-channel fields, only the 4th is consumed by that subsystem (an index into a secondary table); the other 3 feed unrelated boot-time/display functions. See [`motor-subsystem-unlock.md`](../investigations/motor-subsystem-unlock.md). **Remote sender confirmed, two call sites**: `FUN_00005a8c(4)` at `0x1039e` in `FUN_00010258` — sent when the user clicks `"Continue"` on the `"Motor <N>: Choose type"` screen once all four motors have an assigned type (the full displayed-string -> input -> sender -> bytes chain is closed for this site); and `0xcb4c` in `FUN_0000c440`'s bulk-push tail — **that call site's real-world trigger is now CONFIRMED**: `FUN_0000c440` is called, unconditionally, exactly once per Remote power-on/reset (`Reset_Handler` → `FUN_00016900` → `FUN_0000fdf0`), and again after any real ~5000-tick radio-silence gap; `MC4` fires there whenever the function's own `S|`→`P...` round trip succeeds cleanly, regardless of whether any `'+'` frame was actually pushed. See [`auto-mode-and-plus-command.md`](../investigations/auto-mode-and-plus-command.md). A genuine surprise found alongside the original discovery of this call site: **Quick Setup itself is opened by the AutoPilot** (a real `MT<...>|` frame reacting to GPIO motor-connector presence detection), not by any Remote menu action — no Remote-side Quick-Setup menu entry point exists. See [`motor-subsystem-unlock.md`](../investigations/motor-subsystem-unlock.md) and [`action-command-map.md`](../ui/action-command-map.md)'s "Quick Setup" entry | — |
| `I<1-4><0-1>\|` | Remote -> AutoPilot | Per-channel async/query state machine. **Execution-confirmed end to end** (`tools/unicorn/virtual_link.py i`): Remote's `0xb958` builds `I<ch+1><digit>\|` with the mode digit INVERTED (`mode_param=0`->`'1'`, `mode_param=1`->`'0'`); AutoPilot's `0x872e-0x877c` stores that digit verbatim (no re-inversion) into `MODE[channel]` and sets `STATE[channel]=5`. The RX handler does **not** itself schedule the response — AutoPilot's real main-loop poll (`channel_event_monitor__CUSTOM`, `0x8a80`, scans all 4 channels every call) notices `STATE[channel]==5`, and since the busy gate is exhaustively dead (see [`motor-subsystem-unlock.md`](../investigations/motor-subsystem-unlock.md)) completes immediately: schedules event 15 and, only when `MODE[channel]==1` (i.e. only when `mode_param==0`), additionally caches live position into the per-channel config struct as a side effect. The response value itself is `LIVE_POSITION[channel]` regardless of mode — confirmed live for both a positive and a negative value, both signs round-tripping correctly into Remote's own per-channel storage (`0x20001908+channel*4`). See [`protocol-pipeline.md`](../investigations/protocol-pipeline.md)'s Open items for the full trace | `<signed-number>,` (event 15) |
| `LL1\|` / `LL2\|` | Remote -> AutoPilot | First/second limit workflow — **execution-confirmed**: `LL1` clears two globals + a validity flag; `LL2` orders them and sets the flag only if they differ. Neither touches live position, target/config, or `0x20001b14`; no GPIO/MMIO dependency; no other firmware code writes either global with a real value — see [`manual-mode-and-limits.md`](../investigations/manual-mode-and-limits.md). **Both `LL1`'s and `LL2`'s Remote-side senders are now CONFIRMED, and they are the same function**: `FUN_0000de3c`, the same screen that hosts the real live-jog loop (see the `0xF0`/`0xE0` row below). `LL1` is sent 3x as an entry preamble AND 3x again after the first jog phase's click, gated on a real position-query success (`I9\|`/`I1\|`, next row); `LL2` is sent 3x after the second jog phase's click, same gate. Found by an exhaustive whole-image raw-byte scan (exactly one `"LL2\|"` literal anywhere in the image) cross-checked by an independent Ghidra xref scan (exactly one reference, at `0xe114`, inside `FUN_0000de3c`) — no other candidate sender exists. The position query's parsed numeric result is confirmed **not** forwarded into either `LL` send (both remain bare, argument-less frames at the sender, `FUN_000058a8`) — see [`manual-mode-and-limits.md`](../investigations/manual-mode-and-limits.md) | — |
| `I9\|` / `I1\|` | Remote -> AutoPilot | **Sender confirmed** (`FUN_0000b834`, a real position-query helper — sends one of these two, selected by a mode byte `*0x200018e7`, waits up to ~1000-3000 ticks (6 retries), parses a signed decimal response) and **the AutoPilot-side dispatch is now execution-confirmed too, resolving the "same protocol path as `I<channel><mode>\|`?" question** (`tools/unicorn/virtual_link.py i9i1`): neither wire form carries a real mode digit (the literal `'\|'` at that byte offset decodes as a garbage mode value). **`I1\|` silently aliases channel 0** — AutoPilot decodes it exactly as `I<channel=0>\|` and the transaction completes normally through the same real dispatch/monitor/event-15 path `I<channel><mode>\|` uses. **`I9\|` is a real, silent, firmware-level dead end** — channel digit `'9'` decodes to array index 8, which the RX handler happily writes (a real out-of-bounds scratch-RAM write, confirmed live), but `channel_event_monitor__CUSTOM`'s real scan loop only ever visits indices 0-3, so event 15 is **never** scheduled and the Remote's own retry loop just times out. So `I9\|`/`I1\|` remain genuinely distinct from `I<channel><mode>\|` (separate sender, separate storage) and from each other (one completes, one is a dead end) — not "the same protocol path" in any sense that collapses them. Its two call sites are the two "click to confirm a limit position" moments inside `FUN_0000de3c`'s Set-Limits sequence (row above) — success gates whether `LL1`/`LL2` are (re)sent; the parsed value itself is stored at a fixed Remote-RAM scratch slot (`0x200027f0`) and, by exhaustive xref, is never read again by anything. See [`manual-mode-and-limits.md`](../investigations/manual-mode-and-limits.md) and [`protocol-pipeline.md`](../investigations/protocol-pipeline.md)'s Open items | `<signed-number>,` (event 15, same as `I`) |
| `H\|` / `J\|` | Remote -> AutoPilot | Toggle a global flag (opposite directions) | — |
| `0xF0 <payload>` / `0xE0 <payload>` (2nd variant) | **Remote -> AutoPilot — direction now CONFIRMED** | **The real Manual Mode / live-jog wire mechanism**, not a discrete ASCII command. Checked by the AutoPilot's `ascii_dispatcher` (`FUN_00008258`) *before* any ASCII command. Grammar (`0xF0`, fully decoded; `0xE0` structurally similar, not byte-mapped): `<0xF0/0xE0><len><0xFF x4>[<channel nibble><sign+23-bit value>]*<'\|'><seq>`, sent by `FUN_0000be94` (called from the live-jog loop `FUN_0000de3c`, Part 3 of the evidence doc) once per UI tick for as long as the jog wheel is not clicked — real captured frames: idle `b'\xf0\x07\xff\xff\xff\xff\|'`, one record `b'\xf0\x0b\xff\xff\xff\xff\x00LK@\|'` (channel 0, value 5,000,000). AutoPilot's receiver routes each record's channel/value into `FUN_00005274`/`FUN_00004d18` — **the same entry point the `I<channel><mode>\|` command uses** — cross-confirmed via the shared `0x20000180[channel]` array. The per-channel value's exact semantic source (accumulated jog delta vs. live/target position) and the `0xE0` variant's precise field widths remain **UNKNOWN**. See [`manual-mode-and-limits.md`](../investigations/manual-mode-and-limits.md) | — |
| `+<units><reserved>,<confirm>,<confirm>,<channel>,<mode><count><recordFields...>\|` | Remote -> AutoPilot | Previously undocumented; **now confirmed Remote-generated** (see below). Writes up to 3 per-channel "mode sub-record" entries (a signed delta, a 0-100 percentage, a rate divisor, a duration) into the exact `0x20001b40` per-channel motor-config struct `FUN_00007cc0`'s `G`-command target lookup reads, via `FUN_000046c8`/`FUN_00004910` (selected by the `<units>` byte right after `'+'`); when the mode field is `>50`, also calls `FUN_00004ca8` (computes `target = start + delta`, chained across sub-records) and `FUN_000043f0` (persists the whole struct back into the flash-backed `0x12000` buffer — the write-back counterpart to `FUN_00004b64`'s bulk load). The two "confirm" fields must match or the write/persist tail is skipped. **AutoPilot side: static-analysis-only, disassembly-confirmed** (every literal-pool address resolved directly against the compiled image): the delta field is copied from the wire with no clamp toward live position, so mode `1`'s target after a `'+'` write should equal `live_position_at_write_time + wire_delta` — a real, protocol-reachable way to drive `FUN_00006fd8`'s move distance past its `8`-unit threshold. **Remote side: confirmed Remote-generated, statically and concretely** — `FUN_000049c4` builds this exact frame (byte-for-byte match to the schema above, including the confirm1==confirm2 invariant and the same `+0xc`/`+0x10` delta convention), called from the Auto-Mode configuration screen state machine (`FUN_0000e670`, each call gated behind a real confirmation wait) and from the `'S'`-handler's bulk "push all channels' stored config" path (`FUN_0000c440`, mode `0x62` — the one mode value confirmed to cross the AutoPilot-side `>50` compute+persist threshold). **AutoPilot side: now concretely confirmed end to end for the `mode=0x62` bulk-push call** — a real `FUN_000049c4`-built `'+'` frame, delivered through the real AutoPilot dispatcher (no full boot needed; entering directly at the real dispatcher call site, the same established boundary every other command in this table uses), produces `target=500` for a wire delta of `500`, dirties the persisted buffer, and a subsequent real `G010|` (channel 0, type 1, also from the Remote's real builder) drives `FUN_00006fd8` to `distance=500`, crossing its real `8`-unit threshold (move-committed flag observed `=1`) — see `tools/unicorn/virtual_link.py plus`. The three interactive Auto-Mode screen confirmations (mode `0`/`0x14`) were not concretely exercised this pass and are known, by disassembly, not to cross the persist threshold by themselves. **The `mode=0x62` bulk-push trigger is now CONFIRMED, precisely**: `FUN_0000c440`'s own `S|`→`P...` round trip succeeding is the gate (any clean response, independent of its value); the real callers are the Remote's own boot sequence (unconditional, once per power-on) and a debounced retry on specific inbound-AutoPilot bytes, re-armed only after a real communication gap — not a vague "reconnect" hypothesis. The push loop itself additionally requires a separate UI-set flag (`0x20000fa0`) that the boot sequence never sets, so a literal cold boot's push is empty (only `MC4` fires); see [`auto-mode-and-plus-command.md`](../investigations/auto-mode-and-plus-command.md). For the interactive screens, confirming/saving a programmed Auto Mode move segment (A/B/C/D points, duration/ramp/delay/loop) remains the working hypothesis, unproven — see [`motor-config-persistence.md`](../investigations/motor-config-persistence.md), [`auto-mode-and-plus-command.md`](../investigations/auto-mode-and-plus-command.md), and [`auto-mode-and-plus-command.md`](../investigations/auto-mode-and-plus-command.md). Full workflow placement (which screen, which of the four interactive call sites — not three, see [`auto-mode-and-plus-command.md`](../investigations/auto-mode-and-plus-command.md) — what stacks with what) is in [`action-command-map.md`](../ui/action-command-map.md)'s Auto Mode deep dive | — |
| `D<value>,\|` | Remote -> AutoPilot | Writes a 32-bit numeric field into the persisted config buffer (the same buffer backing the `0x12000` flash region) at logical offset `0x15`, then writes a `0xDE` marker byte at offset `0x19`; a real boot-time reader (`FUN_00004c20`) checks that marker and, if present, reads the value back. If the written value differs from what's already stored, this also sets the buffer's dirty/save-pending flag. **Execution-confirmed, concretely, full round trip**: requires the trailing comma (`D1234,\|` parses cleanly and writes the exact value; a bare `D1234\|` dispatches but the field parser runs past the packet into adjacent memory since its only real terminator is a literal comma; an 8-byte `D12345,\|` failed to dispatch at all, an unexplored framing curiosity). The real save path fires naturally afterward (real GPIO/tick behavior, no fabrication) and, once the driver object's page-size field was correctly modeled from `NVMCTRL.PARAM`, actually mutates flash at `0x12000` — confirmed by a direct memory dump matching the written value/marker byte-for-byte. A genuinely fresh boot from that mutated flash recovers `1234`/`0xDE` through the real load path with zero commands re-sent — see [`motor-config-persistence.md`](../investigations/motor-config-persistence.md), [`motor-config-persistence.md`](../investigations/motor-config-persistence.md), and [`motor-config-persistence.md`](../investigations/motor-config-persistence.md) | — |
| `T<0 or 1023>,<1 or 0>,\|` | AutoPilot -> Remote | Found while tracing the 3.5mm trigger-input reported bug — a real, previously undocumented outbound frame, **execution-confirmed concretely, both shapes**. Sent from inside the `MC4`-gated motor-phase/ramp state machine (`phase_ramp_state_machine__CUSTOM`), only when trigger-status reporting is armed (`0x20003120 != 0`, set by `TR1\|`, above), rate-limited to once per ~500 firmware ticks, reporting a live `digitalRead()` of the trigger circuit's PB05 pin: `"T1023,0,\|"` when PB05 reads high that cycle, `"T0,1,\|"` when low. Concretely reproduced entering at the state machine's own real function start (`0x8e18`) with zero fabricated register state, sent through the AutoPilot's already-proven TX wrapper (`0x8c10`). A level-sampled poll with no debounce/history between checks. **When reporting is disarmed (`TR0\|`, the default) instead**, a related but distinct path (same PB05 pin, opposite polarity, gated behind four additional idle-state conditions) reaches a real reload of the persisted motor-target config (`config_loader__CUSTOM`/`FUN_00004b64`) rather than sending this frame — see [`trigger-input.md`](../investigations/trigger-input.md). **Remote-side effect CLOSED**: parsed and stored by the Remote's real inbound dispatcher (`FUN_00010ce4`'s own `'T'` branch), consumed only by a real UI screen's own redraw (`FUN_0000fa10`, scales the first field to `field1*3300/1023` and colors it by the second) — concretely confirmed to send nothing back, for both real frame shapes — see [`trigger-input.md`](../investigations/trigger-input.md) | pure display update — no outbound command |

## Lower-confidence / unresolved

- `Y...,`, `+...`, `A...`, `X1`/`X2` — top-level parser branches exist;
  command semantics only partially understood. (`D...` moved up to the
  high-confidence table above this pass.)
- `V<decimal>,\|` — construction confirmed on the Remote side, but no
  matching top-level branch found in the AutoPilot's main text dispatcher.
- `MS\|`, `MR\|`, `MM\|`, `KK\|`, `E1,...\|`, bare `W\|` — the Remote
  actively transmits these, but they don't fit the AutoPilot's visible
  dispatch tree (see [`docs/investigations/protocol-pipeline.md`](../investigations/protocol-pipeline.md)
  for why that dispatch-tree model itself is now known to be incomplete —
  these may yet turn out to be reachable through paths the static pass
  didn't find). Tracked in [`open-questions.md`](open-questions.md).
  (`N\|`'s Remote-side sender is now confirmed — see the `B0\|`/`TR0\|`
  row above; whether it fits the AutoPilot's dispatch tree is still
  untouched.)
- ~~`I9\|` / `I1\|` short forms~~ — **moved up to the high-confidence
  table above this pass**: sender confirmed (`FUN_0000b834`, the
  Set-Limits position-query helper), see
  [`manual-mode-and-limits.md`](../investigations/manual-mode-and-limits.md).
- `MT<b0><b1><b2><b3><x>\|` — **AutoPilot -> Remote** (opposite direction
  from every other row in this table). Real, disassembly-confirmed and
  concretely-produced AutoPilot builder (`0x740c`-`0x74dc`), encoding four
  real GPIO motor-connector presence probes (a guarded, 2-valued/boolean
  read per channel, slot order `A→b0, C→b1, B→b2, D→b3`) as one digit
  each; the Remote's inbound handler (`FUN_00010ce4`) turns each `'0'`
  into per-motor type `"Not connected"` and opens the Quick Setup
  "Choose type" screen. **Scheduling — CONFIRMED, exhaustively**: sent
  exactly once per physical boot/MCU reset, unconditionally, as a plain
  step of `sketch_setup()` (reached by a single, exhaustively-confirmed-
  unique static path — `sketch_setup` → `FUN_00007770` →
  tail-jump `0x7334` — with no other entry anywhere in the image), after
  the startup reference/input routine and radio-ID handshake complete and
  before `setup()`'s own `MC4`-wait loop begins. Never periodic, edge/
  change-driven, or reconnect-driven — `setup()` itself runs exactly once,
  ever. The 5th field (`<x>`) is a single byte at `0x20001fc0`, written by
  the startup reference/input routine, always `'1'` or `'2'` in practice.
  See
  [`motor-subsystem-unlock.md`](../investigations/motor-subsystem-unlock.md)
  and, for the Remote-side reaction (unchanged this pass),
  [`motor-subsystem-unlock.md`](../investigations/motor-subsystem-unlock.md)
  Part 4.
